# ADR-001: 직접 임베딩 (Atlas auto-embed 미채택)

- **상태**: 채택됨 (2026-07-29)
- **관련**: [adr-002 (모델 선택)](adr-002-embedding-model.md), [search-architecture.md](../search-architecture.md)

## 맥락

앱 자연어 검색·AI 챗봇·공개 MCP 서버가 공유할 벡터 검색 인프라가 필요하다. 벡터를 만드는 방식은 두 가지:

- **Atlas auto-embed**: 인덱스 정의에 `autoEmbed` 필드를 선언하면 Atlas가 색인·질의 시점에 임베딩을 대신 생성. 동기화 코드 0줄.
- **직접 임베딩**: 크롤러가 임베딩 API를 호출해 벡터를 문서 필드로 저장하고, Atlas는 저장·검색만 담당.

## 결정

**직접 임베딩.** 크롤러의 `notices_embedding` 모듈(신설 예정)이 문서 벡터를 생성·소유하고, `notices` 컬렉션에 `contentEmbedding` 필드로 저장한다.

## 근거

1. **로드맵에 doc↔doc 유사도 기능이 있다** (중복 공지 탐지, 관련 공지). auto-embed가 만든 벡터는 내부 예약 네임스페이스(`__mdb_internal_search`)에 저장되어 **애플리케이션이 읽거나 내보낼 수 없다** — 문서 A의 벡터로 문서 B를 찾는 기능이 원천 불가능.
2. **auto-embed는 preview 기능** — MongoDB 문서가 프로덕션 사용을 명시적으로 비권장 (2026-07 기준).
3. **추론이 클러스터를 떠난다** — auto-embed 추론은 클러스터 리전과 무관하게 US Google Cloud 멀티테넌트 서비스에서 실행. 데이터 이동 + 전송 비용.
4. **M10+ 오토스케일링 강제** — dedicated 클러스터에서 auto-embed를 쓰려면 스토리지·티어 오토스케일링을 켜야 함(M10은 M30까지 확장 허용 필요). 임베딩 비용보다 클러스터 요금 변동이 훨씬 큰 리스크.
5. **동기화 로직의 한계비용이 낮다** — auto-embed의 최대 가치는 "동기화 대행"인데, 같은 패턴(`contentHash` 비교 stale 판정 → 배치 API 호출 → `$set`)이 이미 `notices_summary` 모듈에 구현되어 있어 미러링만 하면 된다.

## 대안과 기각 사유

- **auto-embed 단독**: 벡터 미노출로 유사도 기능 불가 (근거 1). 기각.
- **검색은 auto-embed + 유사도용 벡터만 직접**: 같은 텍스트를 두 번 임베딩하는 낭비 + "어느 게 진짜냐" 이원화. 기각.
- **auto-embed를 2주 측정 도구로만 사용 후 폐기**: 코드 0줄로 Voyage 한국어 품질을 잴 수 있는 장점이 있었으나, 오프라인 로컬 임베딩 비교(adr-002)로 같은 답을 더 정확하게(후보 모델까지 함께) 얻을 수 있어 불필요. 기각.

## 되돌리기 비용

원본(`contentText`)이 DB에 남아 있으므로 벡터는 언제든 재생성 가능한 파생물이다. 6,500건 재임베딩은 수 분·무료 한도 내 (adr-002 참조).

## 재검토 조건

- auto-embed가 GA + 벡터 export 지원 + 오토스케일링 강제 해제가 **모두** 충족될 때.
